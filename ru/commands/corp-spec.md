description: Черновик делта-спек(и) для истории через интервью; при необходимости разворачивание по репозиториям (поток аналитика)
---
Вы составляете спецификацию для истории {{args}}.
Следуйте скилам corp-drill-down (все факты о системе) и corp-verification (все заявления о готовности).

1. ПРОЧИТАЙТЕ + ПРОВЕДИТЕ ИНТЕРВЬЮ, один раз. Получите историю, её вики-страницы и вложения через
   MCP-инструменты трекера/вики. Прочитайте openspec/index.md и ТОЛЬКО те живые спецификации,
   которые затрагивает история; следуйте corp-drill-down (центральный каталог → индекс репозитория →
   живые файлы; репозиторий главнее; ≤3 перехода). Проверьте каждый факт контракта по живому коду.
   Проведите интервью с аналитиком — ПО ОДНОМУ вопросу за раз, предпочтительно с вариантами ответа —
   пока требования и сценарии Given/When/Then не станут однозначными.
   Проводите интервью ОДИН раз на уровне истории, даже если задействовано несколько репозиториев:
   требования общие, поэтому интервью по каждому репозиторию задаёт одни и те же вопросы N раз и
   порождает N разных ответов.

2. ОПРЕДЕЛИТЕ ФОРМУ, затем ПОДТВЕРДИТЕ, прежде чем что-либо создавать.
   Посчитайте репозитории, которые затрагивает история.
   - ОДИН репозиторий → путь одного репозитория. Переходите к шагу 3.
   - БОЛЬШЕ ОДНОГО репозитория → есть ли настоящий общий контракт (форма или протокол, пересекающий
     границу)? Если НЕТ, скажите «это не кросс-репозиторное изменение; это N независимых историй» и
     остановитесь — не разворачивайте. Если ДА, переходите к шагу 4.
   Прежде чем создать любой тикет, ветку, коммит или PR, изложите план и ДОЖДИТЕСЬ аналитика:
   какие репозитории, какой из них producer, какие тикеты уже существуют, какие вы создали бы и
   сколько PR это откроет. Никогда не разворачивайте молча.

3. ОДИН РЕПОЗИТОРИЙ. Создайте OpenSpec-изменение (proposal + делта-спека) в этом репозитории через
   поток opsx. Добавьте проверенные факты в research.md как указатели (path#Lx-Ly + вывод одной
   строкой). НЕ создавайте design.md или tasks.md — планирование происходит в момент взятия в работу.
   Выполните: bash tools/verify-docs.sh — исправляйте до зелёного.
   ПЕРЕДАЧА (сделайте это сами — аналитик никогда не трогает git): создайте/переключитесь на ветку
   изменения с именем feature/<TICKET> для тикета этой истории, закоммитьте папку изменения,
   запушьте и откройте (или обновите) PR со спецификацией. Опубликуйте резюме спецификации + ссылку
   на PR обратно в историю. Готово.

4. КРОСС-РЕПОЗИТОРНО — СНАЧАЛА ТИКЕТЫ, исходя из того, что уже существует.
   Посмотрите на дочерние тикеты, прикреплённые к родительской истории.
   - Дочерние уже есть → используйте их. Сопоставьте каждый дочерний с его репозиторием. Если у
     репозитория нет дочернего тикета или дочерний не называет репозиторий, ОСТАНОВИТЕСЬ и спросите
     аналитика — никогда не угадывайте владельца.
   - Дочерних нет → спросите аналитика: «задействовано N репозиториев; создать по одной дочерней
     истории на репозиторий, или вы создадите сами?» Следуйте ответу. Если создают они — дождитесь
     и перечитайте.
   РОДИТЕЛЬСКАЯ история является тикетом контракта в системном сторе — своего дочернего тикета у неё нет.

5. СНАЧАЛА КОНТРАКТ. На ветке feature/<parent-ticket> в СИСТЕМНОМ СТОРЕ создайте/обновите
   спецификацию контракта (шаблон store-contract.md). Факты формы живут там и больше нигде.
   Выполните verify-docs, закоммитьте, запушьте, откройте PR стора, опубликуйте ссылку на PR в
   родительской истории.

6. ПО КАЖДОМУ РЕПОЗИТОРИЮ, по одному:
   a. Ветка feature/<child-ticket> (именование: conventions/branching.md).
   b. Напишите OpenSpec-изменение: proposal + СОБСТВЕННУЮ делта-спеку этого репозитория, которая
      ССЫЛАЕТСЯ на контракт стора по id спецификации и id стора — никогда не пересказывает форму.
      Включите строку получения:
      `openspec show <contract-spec-id> --type spec --store <store-id>`
      Добавьте проверенные факты в research.md как указатели. Никаких design.md, никаких tasks.md.
   c. Выполните: bash tools/verify-docs.sh — исправляйте до зелёного. Линтер split-brain должен
      пройти; если он сработал — вы пересказали факт контракта, удалите его и поставьте ссылку.
   d. Закоммитьте как feat(<child-ticket>): <текст>, запушьте, откройте PR, опубликуйте ссылку на PR
      в тикете.

7. ГЕЙТЫ. В каждом дочернем тикете реализации зафиксируйте: порядок одобрения (сначала контракт),
   порядок реализации (сначала producer), порядок мержа (producer → consumers → контракт стора
   последним) и то, что изменение контракта останавливает работу во всех репозиториях. Пометьте
   каждый дочерний тикет как заблокированный родительским.

8. В родительской истории опубликуйте карту тикет → репозиторий → роль и планируемое окно мержа.

9. ПРОВЕРЬТЕ перед отчётом: каждый дочерний тикет связан и сопоставлен репозиторию; у каждого
   репозитория есть ветка, запушенный коммит и открытый PR; verify-docs зелёный в каждом.
   Приложите доказательства. Никогда не заявляйте о готовности без них.
