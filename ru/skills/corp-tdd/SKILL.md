## Железный закон
Никакого продакшн-кода без предварительно написанного падающего теста. Никаких исключений для «тривиальных»
изменений — тривиальные изменения с тестами остаются тривиальными; тривиальные изменения без тестов становятся инцидентами.

## Два уровня (это часть, специфичная для стека)
Уровень FAST — внутренний цикл, запускается после КАЖДОГО зелёного шага, должен укладываться в секунды:
- JVM: обычные модульные тесты JUnit. Без контекста фреймворка. Мокайте только на границах модулей.
- Потоковая обработка: operator-test harness потокового обработчика для операторов
  и UDF — в пределах JVM, без кластера.
- JS-фронтенд: компонентные тесты (в стиле testing-library), тесты чистых функций.
Уровень SLOW — запускается на границах ЗАДАЧ и перед PR, никогда внутри микро-цикла:
- JVM: интеграционные тесты контекста на Testcontainers. Уважайте кэширование контекста: общий абстрактный
  базовый класс, статические контейнеры, никакого разбросанного по классам сброса контекста / мок-бинов — сбитый
  кэшем набор тестов превращает 2 минуты в 15 и убивает всю эту дисциплину.
- Потоковая обработка: конвейерные тесты на embedded-кластере.
- JS-фронтенд: прогон E2E/визуальных тестов (запустите приложение; скриншоты — это доказательство).
Баги DI/связывания всплывают ТОЛЬКО на медленном уровне — задача, затрагивающая DI-связывание, не считается
завершённой на одном лишь зелёном быстром уровне.

## Цикл (на каждую задачу в tasks.md)
1. RED: напишите тест из сценария задачи. Запустите его. УВИДЬТЕ, как он падает с ожидаемым сбоем —
   тест, который проходит сразу, ничего не проверяет; остановитесь и исправьте тест.
2. GREEN: минимальный код, чтобы пройти. Не поддавайтесь искушению добавить незапрошенное поведение.
3. Запустите быстрый уровень. Рефакторьте только на зелёном. Перезапустите.
4. По завершении задачи: медленный уровень для затронутых областей. Вставьте вывод прогона в tasks.md как доказательство,
   отметьте галочку, перезапишите заголовок состояния.

## Запрещённые приёмы
Ослабление проверки ради прохождения · удаление/пропуск падающего теста · проверка деталей
реализации (приватные методы, счётчики вызовов) вместо поведения · отметка задачи выполненной без вставленного
вывода теста · написание тестов после кода «для экономии времени» (это не TDD, это декорация).
