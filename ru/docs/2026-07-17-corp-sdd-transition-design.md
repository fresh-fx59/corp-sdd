# Переход на корпоративную SDD — полный дизайн

**Дата:** 2026-07-17 · **Статус:** УТВЕРЖДЕНО оператором 2026-07-18 · **Владелец:** оператор (корпоративная команда основной работы)
**Утверждённый базовый вариант:** Вариант A (минимальный тулинг). Вариант B (неограниченный OSS) задокументирован как путь апгрейда.

## 1. Контекст и цели

Кросс-функциональная корпоративная команда (аналитики, разработчики, ручные тестировщики, SDET, DevOps) переходит на спецификационно-ориентированную разработку (SDD). Окружение:

- **Агент:** **корпоративный порт агент CLI** (поправка 2026-07-18: не апстримный — каждый факт уровня харнесса в этом документе, процитированный из апстримной документации агент CLI, т. е. раскладка `.agent/`, форматы команд/скиллов, конфигурация MCP, headless-флаги, экспорт OTLP, является предположением, которое нужно перепроверить через зонды обнаружения порта §0a руководства по внедрению), работающий на самостоятельно размещённой **open-weight модели с большим контекстным окном** через OpenAI-совместимый шлюз — *предоставляется как есть; наши только клиентские настройки*. Эффективная используемая длина всё равно деградирует задолго до заявленного предела (бенчмарки оценивают её в ~50–65%), поэтому дизайн сохраняет дисциплину малых артефактов / drill-down как оптимизацию качества — но ни один класс работ не требует особой маршрутизации контекста.
- **Продукт:** большой, преимущественно на JVM-стеке (многомодульный JVM-эстейт); задания потоковой обработки (stream processing) (обработка в реальном времени / нормализация / обогащение, stateless — восстановление из savepoint не используется); JS-фронтенд; шина событий + REST; колоночное OLAP-хранилище/кэш/реляционное хранилище; продукты-потребители используют его данные ниже по потоку. Визуальный dataflow-инструмент присутствует, но **полностью вне области SDD** (§14). Графовая база данных не используется.
- **Репозитории:** множество git-репозиториев; некоторые содержат по нескольку независимых модулей. **CI: самостоятельно размещённый CI.** JVM LSP MCP-сервер уже развёрнут (имя уточняется — класса Serena); он является частью базовой конфигурации, а не дополнением.
- **Политика тулинга:** только OSS; продукт-агностично к трекеру/вики/форджу (организация мигрирует с self-hosted ALM-системы на внутренние инструменты, говорящие на **MCP**); члены команды могут клонировать все репозитории локально; **предпочтителен минимальный тулинг** (утверждён Вариант A); никаких внешних сервисов во внутреннем цикле.
- **Цель дизайна №1:** минимальное трение — ИИ должен упрощать работу каждой роли, а не добавлять церемоний. Никто не меняет свой основной инструмент; ни у кого не растёт объём набора текста.

База доказательств: три раунда исследований + состязательная критика (2026-07-16/17), зафиксировано в `corp-sdd-transition-project-log.md`. Заслуживающих доверия опубликованных числовых показателей результатов корпоративной SDD не существует — организация должна снять свой базовый уровень и измерять собственные (см. §11–12).

## 2. Решения с одного взгляда

| # | Решение | Почему (кратко) |
|---|---|---|
| 1 | **Комбо через выборочный вендоринг**: OpenSpec (закреплён) = жизненный цикл спеки; 4–6 скиллов, завендоренных из superpowers (MIT) = дисциплина исполнения; корпоративные команды связывают их | По отдельности ни того, ни другого недостаточно: у `apply` в OpenSpec нулевая дисциплина тестов/верификации (проверено в исходниках), у superpowers нет жизненного цикла спеки и нет работающего авто-триггера на агент CLI (живой тест провалился) |
| 2 | **Явные команды, никогда авто-триггер** | Единственный механизм вызова, надёжно доказанный на агент CLI; поддаётся аудиту |
| 3 | **Спеки колокированы по репозиториям** (атомарные PR спека+код) + **система-хаб «hub-and-spoke»** для кросс-репозиторных контрактов/индекса | В git нет атомарного кросс-репозиторного PR; колокированные документы — доказательно выживающий вариант (g3doc, дефолт OpenSpec); только централизованно = задокументированная топология дрейфа |
| 4 | **Федеративный drill-down индекс**: генерируемый индекс по каждому репозиторию; хаб хранит тонкий агрегат + вертолётный обзор; агент погружается центр→репозиторий→живой код; *репозиторий выигрывает по построению* | = архитектура Backstage; соответствует потолку контекста; центральный индекс — это маршрутизация, никогда не авторитет |
| 5 | **Трёхслойное состояние**: живые спеки / генерируемые карты / append-only ADR | Согласовано по волатильности; генерируемый контент не может протухнуть («источник — это вход») |
| 6 | **Требования долговечны, планы одноразовы**: спека в момент истории, дизайн/задачи в момент вытягивания на реализацию | Схлопывает окно устаревания; регенерация дёшева при наличии агента |
| 7 | **Слой-диспозер**: один детерминированный скрипт верификации, 4 триггера, контракт границы записи в стиле Hermes | «Модель предлагает, код диспозирует»; вывод агента валидируется, а не принимается на веру |
| 8 | **Промежуточные файлы вместо большого контекста**: папка изменения = машина состояний на диске | эффективный контекст < заявленного даже при большом окне; многостадийность с todo; сессии возобновляются из файлов, а не из транскриптов |
| 9 | **Промпты советуют, CI принуждает** — но проверки запускаются **сначала локально** (pre-commit + самопроверка агента); CI — только подстраховка | CI идёт последним в потоке организации; обратная связь должна быть в момент записи |
| 10 | **Визуальный dataflow-инструмент полностью исключён из SDD** (не в git; правится руками на проде) | Нечего версионировать, нечего гейтить — помечено как постоянный риск вне этого дизайна |
| 11 | **Сначала Вариант A, Вариант B как следующая фаза** (не опциональная роскошь) | Минимальный след доказывает поток; элементы B входят на той фазе, где каждый окупается (§11) |

## 3. Архитектура (четыре слоя)

```
L3 ENFORCEMENT (self-hosted CI backstop — helicopter level, detailed later)
   held-out checks the agent can't see/edit: contract tests (Pact-class),
   schema compatibility, migration lint; credential-scoped jobs
L2 EXECUTION DISCIPLINE (corporate-owned, per-repo, versioned in git)
   vendored skills: tiered-TDD-jvm, verification-before-completion,
   systematic-debugging, code-review, drill-down protocol, stack skills
   (jvm-test-tiers, stream-harness-tdd) + ~6 corp commands
L1 SPEC LIFECYCLE (OpenSpec, pinned)
   living capability specs + delta changes per repo; system store hub;
   wiki mirror + tracker links via MCP
L0 MODEL & BRIDGES (given)
   the agent CLI → corporate gateway (settings tweak only); MCP to tracker/wiki;
   local clones of all repos via repos.yaml manifest
```

Всем управляют два принципа: **(a)** промпты и скиллы носят рекомендательный характер — каждое правило, которое никогда не должно нарушаться, принуждается детерминированным кодом (L2→диспозер, L3→CI); **(b)** во все рабочие потоки агента входят через явные команды.

## 4. Топология, индекс и состояние

### 4.1 Hub-and-spoke

- Каждый код-репозиторий владеет `openspec/` (живые спеки + папки изменений) → спека и код сливаются в **одном PR**, откатываются вместе, версионируются вместе с релизными ветками бесплатно.
- Один репозиторий **системного хаба** (обычный git — *без зависимости от stores-beta функций OpenSpec*): кросс-репозиторные интеграционные контракты, конвенции организации + схемы, вертолётное описание системы, реестр владения capability (capability → владеющий репозиторий; остальные объявляют `consumes`, никогда `owns`), манифест клонирования `repos.yaml` и агрегированный индекс.
- **Правило размещения:** спека живёт в репозитории, куда попадает её реализующий PR; нет единого дома → хаб.
- **Правило split-brain (уровень блокера):** каждый контрактный факт живёт ровно в одном месте; спицы ссылаются, никогда не повторяют (проверяется линтером).
- Релизные ветки: колокация решает версионирование на уровне спиц; центральный индекс/хаб описывают только `main` и в остальных местах служат только для обнаружения.

### 4.2 Федеративный drill-down индекс

- **По каждому репозиторию** `openspec/index.yaml` (машинный) + `index.md` (человеческий): идентичность (написана вручную, крошечная) + список capability, *указатели* на контракты (ID + путь, никогда форма), карта модулей — **всё генерируется закоммиченным скриптом** из `openspec/` + манифестов сборки; канонизированный вывод; штампуется `generated_from: <SHA>`.
- **Центральный агрегат**: одна запись на репозиторий (ссылка, описание в 1 абзац, однострочники capability, исходный SHA+таймстемп), **пушится CI спицы при слиянии** + ежедневное полное пересканирование; при плохом входе сохраняется последнее-хорошее и помечается `stale` с причиной; невалидный репозиторий показывается **красным** на вертолётном обзоре, никогда не опускается молча; переносы оставляют tombstone-редиректы.
- **Контракт drill-down** (завендоренный скилл): центральный индекс → собственный индекс целевого репозитория → живые файлы в **локальном клоне** (скрипт синхронизации обновляет; линтер предупреждает, когда клон отстаёт от origin). Центр — только навигация; *репозиторий выигрывает по построению*; свежесть = сравнение штампа SHA с HEAD. Бюджет: ≤3 содержательных перехода, сначала поиск, без предзагрузки соседей.
- Порядок сборки контекста (модель среднего уровня, lost-in-the-middle): спеки в начале → навигация в середине (одноразовая) → код → **повторная вставка проверенных фрагментов контракта внизу** непосредственно перед генерацией. Потолок одного артефакта ~4K токенов; спеки адресуемы по секциям.

### 4.3 Трёхслойное состояние (усиленное)

| Слой | Содержимое | Механика |
|---|---|---|
| Живые спеки | текущее поведение по каждому capability | обновляется только шагом архивации; контрактные факты **встроены из источника** (embed-verify в CI), список front-matter `sources:` управляет флагами свежести; проверяемые утверждения становятся правилами ArchUnit, а не прозой |
| Генерируемые карты | только навигация | **два вида**: скелет модулей/зависимостей из сборки (depgraph-maven-plugin / граф Gradle / jdeps — детерминированный, невосприимчивый к сбою дубликата символа у карт в стиле PageRank) + ранжированные карты по каждому модулю; ≤1–2K токенов каждая; CI regenerate-and-diff |
| Заметки (ПОЧЕМУ) | решения и обоснования | **append-only ADR** (неизменяемые, ссылки superseded-by) — черновик агента при архивации (доказательство: ~50% ручных внедрений ADR умирает); допускается одна крошечная изменяемая заметка «текущее состояние» на репозиторий |

Жёсткие правила: файлы состояния **указывают на истину, никогда её не кешируют**; всё, утверждаемое как контракт, встраивается/верифицируется из живого кода.

## 5. Поверхность команд и роли

Всю методологию несут шесть глаголов (в рамках проекта, явные):

```
corp spec <story>   analyst+agent: MCP-pull story/wiki → Socratic interview →
                    delta spec (reqs + G/W/T scenarios) → wiki mirror; git invisible
corp plan           dev: spec → design/tasks — generated AT PULL TIME (Decision 6)
corp implement      dev: per-task loop — failing test from scenario → code →
                    verify-with-evidence → next; pauses on ambiguity; self-check
                    via disposer before proposing any commit
corp review         structured pre-review of a diff before humans spend time
corp test-plan      tester: scenarios → manual checklist in tracker
corp autotest       SDET: scenarios → autotest skeletons
```

**Спека пишется один раз, потребляется четыре раза** (план, тесты, чеклист тестировщика, автотесты) — это и есть структурное упрощение. Дельты ролей: аналитик = интервьюируемый+редактор вместо машинистки документов (никогда не касается git); разработчик = рулит и ревьюит, может написать любую историю руками (opt-in на время перехода); тестировщик = чеклист, выведенный из сценариев, вместо реверс-инжиниринга области; SDET = ревьюит генерируемые скелеты, позже владеет held-out гейтами; DevOps = разовая настройка, всё едет через репозиторий (клон = настроен). События одобрения используют существующий UI одобрения PR у форджа (гейт слияния, а не конвенция) — никаких новых инструментов.

## 6. Циклы дрейфа и обнаружения

**Устаревание очереди** (история ждёт, код движется): в момент истории существуют только предложение + делта-спека (связаны с поведением, устойчивы); все связанные с кодом артефакты генерируются в момент вытягивания. При вытягивании: rebase (конфликты живых спек всплывают как обычные git-конфликты), затем семантический проход свежести помечает дрейф на уровне требований; открытые изменения, затрагивающие тот же capability, перечисляются в момент предложения.

**Обнаружение в середине реализации** (спека ≠ реальность кода): стоп, классифицировать — **(a)** спека неполна → агент составляет черновик поправки к всё ещё изменяемой делте на той же ветке; аналитик одобряет diff через трекер; **(b)** код удивляет, но спека верна → регенерировать дизайн/задачи, спека нетронута; **(c)** спека нереализуема → жёсткий стоп, эскалация с доказательствами. Каждая (a) подтягивает живую спеку ближе к реальности — на раннем этапе (a) частая и является ростом базы спек, а не провалом. Кросс-репозиторный вариант: поправка расходится в PR хаба (2–3 PR, принимаемая цена — см. риски).

## 7. Слой-диспозер

Один скрипт, `scripts/verify-docs.sh`, упорядочен дёшево→дорого, полностью офлайн (инструменты проверены на практике):

1. **Таблица потолков** — жёсткие пофайловые лимиты строк/символов (цикл `wc -l`; напр. index.md ≤300, карта модуля ≤150, tasks.md ≤200, research.md ≤400)
2. **Схемы** — `check-jsonschema` (или ~20-строчный Node-скрипт на ajv+gray-matter) для `index.yaml` + front-matter спеки; **схемы несут лимиты загрязнения** (`maxLength`, `maxItems`, `additionalProperties: false`)
3. **Ссылки+якоря** — `lychee --offline --include-fragments` (ловит битые кросс-файловые якоря заголовков, ~0с)
4. **Embed-ы** — `embedmd -d` (фрагменты контракта побайтово сверяются с источником)
5. **Дрейф генерируемого** — регенерировать индекс/карты, сравнить с закоммиченным, падать при различии
6. **Структура** — форкнутый `lint-notes.mjs` (Node без зависимостей, ~240 строк): проверки enum/дат во frontmatter, kebab-case, обязательные секции по типу (у делты есть ADDED/MODIFIED/REMOVED; у tasks.md есть заголовок состояния + корректные чекбоксы), биекция индекса, restate-lint, входные гейты стадий, **подсказка по исправлению на каждой ошибке** (то, что позволяет модели среднего уровня самокорректироваться)

**Четыре триггера, один путь кода:** самопроверка агента после записи (write → verify → stderr → regenerate; CI никогда не видит первых черновиков) → **lefthook** pre-commit (блокирует на ERROR; единый бинарник Go — никакого Node для JVM-разработчиков, никакого Python ни для кого) → по требованию → подстраховка CI (идентичный скрипт). Завендоренные бинарники: lychee, embedmd, lefthook. Отклонены: pre-commit.com (Python + сеть), husky (только Node).

**Контракт границы записи** (прецедент Hermes, NousResearch/hermes-agent): захардкоженные потолки живут в версионируемых схемах + таблице потолков; нарушения **отклоняются с текстом исправления** («index.md — 320/300 строк — вынесите детали модулей в карты модулей»), никогда не подрезаются и не авто-фиксятся; бюджеты в символах/строках (независимо от модели); повторяющиеся сбои упираются в circuit breaker (стоп, спросить человека) вместо зацикливания.

**Приёмочный тест для всего дизайна: если индекс репозитория может быть неверным, пока его CI зелёный, дизайн провалился.**

## 8. Промежуточные файлы (многостадийная рабочая память)

Папка изменения — это межстадийная, межсессионная машина состояний агента; сессии остаются малыми, потому что состояние живёт на диске (конвергенция персонального note-vault / OpenAI exec-plans / Manus / Anthropic note-taking):

| Файл | Дисциплина | Роль |
|---|---|---|
| `proposal.md` + delta | долговечный, одобренный | контракт |
| `research.md` | append-only; **указатели, а не полезная нагрузка** (путь/SHA/однострочный вывод) | доказательства drill-down, собранные один раз, читаемые всеми последующими стадиями |
| `tasks.md` | чекбоксы + перезаписываемый на месте заголовок «As of DATE — stage N, next: X» (принуждается линтером) | точка возобновления + прогресс; постоянная перезапись заголовка заодно служит рецитацией против lost-in-the-middle |
| `design.md` | одноразовый, регенерируемый | как, в момент вытягивания |
| decisions | append → ADR при архивации | питание слоя ПОЧЕМУ |

Проверки диспозера покрывают и эти файлы — агент не может загрязнить собственную рабочую память сверх потолков.

## 9. Вариант A — минимальный тулинг (УТВЕРЖДЁН)

Полная спецификация материалов сверх того, что организация уже запускает (фордж, CI, MCP трекера/вики, агент CLI+шлюз):

| Элемент | Что это | Лицензия |
|---|---|---|
| OpenSpec | CLI жизненного цикла спек, **версия закреплена**, принимаются причуды TOML-команд + именования `/opsx:` | MIT |

## 10. Вариант B — неограниченный OSS (следующая фаза, по Решению 11)

Та же архитектура; дополнения ранжированы по ценности на единицу операционной нагрузки (лицензии проверены 2026-07-17). Каждый элемент входит на фазе развёртывания, названной в §11. Примечание: **существующий JVM LSP MCP** организации уже покрывает половину пункта 1, отвечающую за навигацию по символам — подключите его к завендоренным скиллам с первого дня (Вариант A) и добавляйте Serena (oraios/serena, MIT — вероятный кандидат на то, что уже развёрнуто) только если действующий покажет себя слабее.

**Топ-3:**
1. **Zoekt** (Apache-2.0) — триграммный кросс-репозиторный поиск (два небольших Go-сервиса + mirror cron); в паре с существующим LSP MCP для символьно-точного продолжения. Наибольшая дельта качества агента на многомодульном JVM-хозяйстве. *Входит: Фаза 2, когда начинается кросс-репозиторная работа.*
2. **promptfoo** (MIT) — golden-set регрессионные наборы для каждой корпоративной команды/скилла, запускаются при каждом редактировании скилла и любой замене модели; почти нулевая инфраструктура. Страховой полис на случай «модель поменялась под нами». *Входит: на входе в Фазу 2 — защитить скиллы до того, как они распространятся за пределы пилота.*
3. **OTel Collector + Langfuse** (ядро MIT; выделение ee/) — у агент CLI есть **встроенный экспорт OTLP**, поэтому подключить стоимость/латентность/частоту сбоев на команду и по команде почти бесплатно; самостоятельный офлайн-хостинг (реляционное хранилище+колоночное OLAP-хранилище+кэш+MinIO). *Входит: Фаза 3, когда организация спросит «сколько это стоит и где ломается».*

**Средние — когда срабатывает триггер:** **Sveltia CMS** (MIT) форменное редактирование спек для не-git аналитиков (git-коммиты под капотом, ограничены схемой) — *Фаза 2, если аналитики сопротивляются ревью через PR*; **Renovate** самостоятельно размещённый (AGPL — флаг для юристов) для закрепления/обновления OpenSpec, lefthook, скиллов через зеркала внутреннего реестра — *Фаза 3*; self-hosted CI-cron doc-gardener (headless агент CLI + gardener-команда → черновой PR) — *Фаза 3*.
**Роскошь — отложить:** **Backstage** (Apache-2.0, CNCF incubating) как каталожный UI поверх тех же hub-файлов — самая высокая постоянная стоимость в классе, дубликат git-индекса, пока масштаб организации не вынудит UI (заслуживающего доверия более лёгкого OSS не существует); **PR-Agent** (The-PR-Agent/pr-agent, MIT — управление только что перешло от Qodo, закрепите SHA и понаблюдайте два квартала) как независимая линия ревью; OpenHands reviewer (только ограниченный эксперимент); DeepEval; дашборд spec-workflow-mcp (GPL + связан с форматом — стащите только UX).
**Дисквалифицированы при строгом OSS:** Sourcebot (FSL), Arize Phoenix (Elastic License), SaaS-сервис визуального diff (SaaS-политика), Atlas (EULA + платный lint/колоночного OLAP-хранилища), Liquibase 5+ (FSL), Confluent Schema Registry (Community License). Флаги лицензий для юристов: AGPL (Renovate, Doc Detective), GPL (spec-workflow-mcp, если когда-либо используется).

## 11. Поэтапное развёртывание

Опоры доказательств: социальная экспозиция драйвит пробу (+216% эффект сверстников через уровень), но *внедрение ≠ удержание*; предоставление сверху вниз «создаёт доступ, а не мотивацию»; практика golden-path = opt-in → default → require **только после >80% добровольного внедрения** (мандат как ратификация реальности); DORA 2025: ИИ усиливает существующее здоровье системы и повышает нестабильность — следите за метриками второго порядка; снимите базовый уровень до развёртывания; измеряйте только на уровне команды.

**Фаза 0 — Базовый уровень и фундамент (4–6 нед).** Хаб + индекс живые; диспозер + lefthook в 2–3 пилотных репозиториях; скиллы/команды завендорены; проводка MCP; **снятие базового уровня** (DORA-5 из существующих данных + анонимный DevEx-пульс). Пилотные команды выбраны 20/60/20 (евангелист/представитель/скептик). *Выход:* метрики запрашиваемы по каждому пилотному репозиторию; линт зелёный; названы чемпионы; задокументирован путь исключений; один чемпион прогнал полный однорепозиторный жизненный цикл на реальной истории.

**Фаза 1 — Пилот с opt-in (6–12 нед, 2 репозитория, уровень ассистента).** Реальные истории через поток; еженедельные office hours; внутренний демо-день (видимость — рычаг внедрения); чемпионы пишут первые ADR. *Выход (расширение):* ≥60% пилотных изменений фич используют поток добровольно 4 недели подряд; ≥10 заархивированных изменений; **индексы остались зелёными без человеческих усилий**; пульс ≥ базового; переделки + частота сбоев изменений плоские-до-снижения. *Удержание:* внедрение низкое, но удовлетворённость положительная → устранить трение, перезапустить. *Откат:* удовлетворённость существенно ниже базового или деградация надёжности CI / качества ревью, относимая к потоку.

**Фаза 2 — Дефолт с путём исключений (12–24 нед, модуль за модулем).** SDD становится *дефолтом* для работы над фичами (механические проверки блокируют; процесс по умолчанию, не мандат); одобрение спеки через гейт форджа; генерация автотестов SDET; held-out гейт v1 в self-hosted CI (задания с областью учётных данных); разработчики смещаются в сторону ревью — сохраняйте ритуалы парного программирования/менторства, подавайте SDD как *авторство спеки* (смягчение идентичности). **Входит Вариант B:** promptfoo на входе в фазу (регрессионная защита скиллов до их распространения); Zoekt, когда начинаются кросс-репозиторные истории; Sveltia, если аналитики сопротивляются ревью через PR. *Выход:* >80% добровольно по всей организации; lead time плоский-до-улучшения; время ревью на PR не раздувается; частота поправок спек снижается внутри изменений (экспериментальный сигнал).

**Фаза 3 — Required-with-exceptions, устойчивое состояние.** Артефакты спек обязательны для изменений класса фич; исключения логируются, путь остаётся навсегда; квартальный обзор; выборочная headless-автономия для низкорисковых классов через линии агентов self-hosted CI. **Вариант B завершается:** наблюдаемость OTel+Langfuse, гигиена версий Renovate, self-hosted CI-cron doc-gardener; Backstage/PR-Agent остаются отложенными, пока масштаб организации не вынудит их. **Критерий заката:** два подряд квартальных обзора, показывающих относимую деградацию доставки → снятие мандата обратно к дефолту.

## 12. Метрики (только на уровне команды; сначала базовый уровень)

| Метрика | Цель | Примечание |
|---|---|---|
| Добровольное внедрение потока (заархивированные изменения ÷ слияния фич) | ≥60% пилот, >80% фаза-2 | проверять, что коммит спеки предшествует коммиту реализации (анти-геймификация) |
| Удержание (разработчик активен ≥5 из первых 14 дней) | вверх | отделяет попробовавших от оставшихся |
| DORA-5: lead time, частота деплоя, частота переделок, CFR, MTTR | плоско→улучшение; следят за нестабильностью | частота переделок — добавка эпохи ИИ |
| Время ревью на PR | плоско (страховка) | пропускная способность раздувается ровно тогда, когда ревью становится узким местом |
| Частота поправок спеки на изменение | снижение = база спек сходится | **наше/экспериментальное**; в паре с линтом полноты |
| Соотношение отловов pre-commit vs CI | CI ловит → ~0 | доказывает, что диспозер работает локально |
| DevEx-пульс (SPACE: удовлетворённость, поток, ревью) | ≥ базового | требуется перцептивное измерение; METR: самоотчётная скорость ненадёжна (~39 п.п. разрыва) — никогда не гейт |

**Анти-метрики (никогда):** LOC, % написанного ИИ кода, индивидуальная частота принятия, индивидуальные рейтинги.

## 14. Границы области и открытые вопросы

**Границы:** **Визуальный dataflow-инструмент — полностью вне области SDD**: потоки не в git и правятся руками на проде. Этот дизайн не пытается их покрывать; зафиксировано как постоянный операционный риск *вне* программы SDD (неверсионируемые артефакты, редактируемые на проде), заслуживает собственной инициативы когда-нибудь, но не этой. **Графовая БД — не используется; пропущена.** **Потоковая обработка (stream processing)** — применяется TDD на operator-harness/MiniCluster (быстрый цикл in-JVM); гейт savepoint не нужен для текущих stateless real-time заданий — пересмотреть только если появятся stateful-задания с восстановлением. **JS-фронтенд** — зона пилота с наименьшим риском.
**Открыто:** выбор визуальной регрессии для фронтенда (OSS-замена vs исключение с SaaS); юридическое согласование по AGPL-элементам, когда наступят фазы Варианта B; точное имя развёрнутого JVM LSP MCP (подтвердить и подключить в скиллы); **фактическая поверхность capability порта агент CLI** (руководство §0a P1–P8 — ответы параметризуют весь слой команд/скиллов).
