## 1. Спецификации попадали в стор, а не в репозиторий кода — ИСПРАВЛЕНО

Подробно: `2026-08-04-openspec-root-resolution-fix.md`.

**Причина (проверена на OpenSpec 1.7.0, не предположение):** OpenSpec ищет свой корень, поднимаясь
**вверх** от текущего каталога в поисках каталога `openspec/`, и **обход не останавливается на
границе `.git`**. Свежий `git init`-репозиторий внутри `system-store/clones/` определялся как
`system-store`, поэтому каждая написанная агентом спецификация попадала в стор.

Достаточно любого из двух условий: репозиторий кода не был онбордингнут (`openspec init`), либо клон
лежит внутри дерева стора.

**Исключено проверкой:** регистрация стора здесь ни при чём — зарегистрированный стор используется
только при явном `--store <id>`.

**Исправление:** побеждает ближайший `openspec/`. Онбордите каждый репозиторий кода и держите клоны
**соседним** каталогом стора (`"clones_dir": "../clones"`, как и поставляется). Проверка одной
командой: `openspec context`. Механический сторож: `tools/check-openspec-root.sh`.

**Второе исправление:** имя `openspec` в npm — **посторонний пакет-заглушка версии 0.0.0 без
бинарника**. Настоящий CLI — **`@fission-ai/openspec`**. Внутреннее зеркало должно нести именно
scoped-имя.

## 2. Как репозиторий ссылается на контракт стора, не пересказывая его

Подробно: тот же документ, §3b.

В `openspec/config.yaml` **репозитория кода** объявляется:

```yaml
references:
  - corp-store
```

Из собственного комментария в исходниках OpenSpec: инструкции получают **индекс** спецификаций стора
(id, краткое описание, рецепт получения), при этом **«содержимое никогда не встраивается; разрешение
корня не затрагивается»**. Первое и есть «ссылайся, не пересказывай». Второе означает, что объявление
ссылки не может вернуть баг из §1.

Агент получает контракт по требованию: `openspec show <spec-id> --type spec --store corp-store`.
Стор должен быть зарегистрирован на машине (одна команда на машину, не на репозиторий).

**Построен линтер `check-contract-split-brain.mjs`**, которого требовал дизайн: он падает, если
репозиторий пересказал факт контракта — тот же заголовок `### Requirement:` или тот же блок кода — с
указанием файла, строки, владельца и команды получения. В репозитории без `references:` он ничего не
делает. Ограничение названо честно: ловит дословный пересказ, не парафраз.

## 3. Кросс-репозиторные истории: родитель = контракт, по тикету на репозиторий

Подробно: `2026-08-04-corp-sdd-cross-repo-fanout.md`. Заменяет шаги 1–4 в §D harness pack.

```
ABCD-1000  родительская история = КОНТРАКТ В СТОРЕ   ветка feature/ABCD-1000 в system-store
                                                    одобряется ПЕРВОЙ, мержится ПОСЛЕДНЕЙ
  ├─ ABCD-1001  база данных   producer               реализуется первым
  ├─ ABCD-1002  бэкенд        consumer
  └─ ABCD-1003  фронтенд      consumer
```

- Общая **форма** определяется один раз, в сторе. Делта-спека каждого репозитория **ссылается** на
  неё и никогда не пересказывает.
- **`corp-spec` — одна команда** для обоих случаев; она определяет случай по drill-down и
  **излагает план и ждёт**, прежде чем открыть N веток и N PR.
- **Атомарности между репозиториями не существует.** Её заменяет порядок: одобрить контракт первым,
  реализовать producer → consumers, мержить producer → consumers → контракт последним. Окно между
  первым и последним мержем держите коротким (цель — тот же день).
- Одно изменение привычки: **вики перестаёт быть контрактом.** Замысел и повествование остаются там;
  поведение уходит в делта-спеку каждого репозитория, общая форма — в контракт стора.

## 4. Соглашения по веткам и коммитам — теперь проверяются механически

Подробно: `2026-08-04-corp-sdd-setup-task-for-agent.md`, шаги 6–7. Правила: `templates/conventions-branching.md`.

```
ветка            feature/ABCD-1234
сообщение        feat(ABCD-1234): commit message text
```

`tools/check-git-naming.sh` проверяет оба, плюс главное: **тикет в коммите должен совпадать с тикетом
в ветке**. Подключается через `lefthook.yml` (`commit-msg` + `pre-push`).

**Находка, полученная вживую:** **глобальный `core.hooksPath` молча перекрывает локальные хуки любого
репозитория**, включая установку lefthook. Файл хука существовал, был исполняемым и не делал ничего —
всё выглядело зелёным. Проверяйте `git config core.hooksPath` и доказывайте намеренно плохим коммитом.

## 5. Zoekt перенесён из Phase 2 в Phase 0

Подробно: `2026-08-04-corp-sdd-zoekt-setup.md`.

Причина: генерируемый `openspec/index.md` строится из спецификаций и списка модулей — он **никогда не
открывает исходный файл**, поэтому в первый день на brownfield-репозитории в нём **0 capabilities**.
Пока живые спецификации не накопятся, кросс-репозиторный поиск по коду **и есть** карта хозяйства для
агента.

**Ловушка, которая стоит дня:** без `universal-ctags` поиск `sym:` **молча умирает** — индексация
успешна, код возврата 0, ноль результатов, ни одного предупреждения. Агент читает это как «такого
символа не существует». Всегда передавайте `-require_ctags` и проверяйте в логе строку
`symbol analysis finished … symbols=N`.

Ещё две проверенные детали: `POST /api/search` возвращает **HTML**, а не JSON (нужен
`GET /search?q=…&format=json`); поле `.Line` в JSON **всегда `null`**, текст лежит в `Fragments[]`.
И: у `zoekt-webserver` **нет аутентификации** — только localhost или обратный прокси.
