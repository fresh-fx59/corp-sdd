# Corp SDD — схема процесса поставки

> Краткая схема по [FLOW.md](FLOW.md).

```text
Задача / запрос
  │
  ▼
1. СПЕЦИФИКАЦИЯ  — Аналитик, corp-spec
  вход:    только намерение либо задача + вики + действующая спецификация + текущий код
  сначала: если дано только намерение, уточнить его с пользователем до спецификации
  выход:   предложение + изменение спецификации + исследование + ветка + pull request
  выходной критерий: доказательства и проверки прошли во всех затронутых репозиториях
  │
  ▼
2. ПЛАН  — Разработчик, corp-plan
  вход:    одобренное изменение + текущий код
  выход:   design.md (<200 строк) + tasks.md с задачами по риску
  выходной критерий: проверки прошли; разработчик одобрил план
  │
  ▼
3. РЕАЛИЗАЦИЯ  — Разработчик, corp-implement
  цикл:    падающий сценарный тест → минимальное изменение → быстрые тесты → рефакторинг
  выход:   код + тесты + отмеченные задачи + результат запуска тестов
  выходной критерий: все задачи завершены; полный набор и финальные проверки прошли
  │
  ▼
4. РЕВЬЮ  — Ревьюер, corp-review
  проверки: покрытие → соответствие спецификации → честность тестов → корректность → скриптовые проверки
  выход:    замечания с серьёзностью, file:line и исправлением; либо чистый результат
  выходной критерий: блокирующие замечания исправлены; проверки запущены снова
  │
  ├─────────────────────────────┐
  ▼                             ▼
5. ПЛАН РУЧНОГО ТЕСТИРОВАНИЯ    6. ЗАГОТОВКИ АВТОТЕСТОВ
  вход: одобренные сценарии       вход: одобренные сценарии
  выход: чек-лист тестировщика    выход: по одному поведенческому тесту на сценарий
  учесть: регрессию и поиск сбоев пометки: недостающая настройка остаётся TODO; запустить всё возможное
  └──────────────┬──────────────┘
                 ▼
7. АРХИВ ПОСЛЕ СЛИЯНИЯ  — Разработчик или ответственный за релиз
  вход:    слитый pull request + финальные доказательства
  выход:   архивированное изменение OpenSpec и постоянная запись
  выходной критерий: слияние завершено; обязательные записи сохранены
```

## Правила на каждом этапе

- Предложение OpenSpec, изменение спецификации и список задач — договор о поставке.
- Утверждение о завершении требует свежего доказательства.
- Несовпадение спецификации и кода останавливает работу до классификации причины.
- После изменений документации запускаются проверки репозитория: `verify-docs.sh`, проверка индекса, линтер и проверка расхождений контрактов.
- Люди одобряют планы, проводят ручное тестирование, принимают и сливают изменения; автоматизация не заявляет, что сделала это.
