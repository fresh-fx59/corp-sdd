# Командный плейбук SDD — как каждая роль работает с системой

**Дополнение к:** [дизайну](../specs/2026-07-17-corp-sdd-transition-design.md) (почему это работает именно так) и [руководству по внедрению](2026-07-18-corp-sdd-implementation-guide.md) (как это было построено). Этот документ — для **людей, которые пользуются системой ежедневно**. Выдайте каждой роли её раздел плюс «Правила для всех».
Имена команд (`corp-spec` и т. д.) — это значения по умолчанию; ваш реальный синтаксис вызова берётся из настройки порта (`port-facts.md` в системном хранилище); поток одинаков в любом случае.

## Поток на одной странице

```
story in tracker
  → ANALYST  corp-spec     agent interviews you → delta spec → you approve (wiki/tracker)
  → DEV      corp-plan     agent plans against TODAY's code → you approve tasks
  → DEV      corp-implement  agent codes task-by-task, tests-first → you steer & review
  → PR       spec + code together → team review as always → merge
  → TESTER   corp-test-plan  checklist from the same scenarios → manual pass
  → SDET     corp-autotest   autotest skeletons from the same scenarios → you harden
  → DEV      corp-archive    (on main, after merge) delta folds into the living spec,
                             ADR drafted, indexes & catalog update themselves
```

Спека пишется **один раз** и потребляется **четыре раза** (план, тесты реализации, ручной чек-лист, автотесты). Именно здесь ваше время возвращается.

## Правила для всех

1. **Во время пилота поток подключается по желанию для каждой истории.** Старый способ остаётся легальным. Если вы пропускаете поток, добавьте одну строку в историю, где это сказано, — вот и весь процесс исключения.
2. **Диспозер — это закон.** Если `verify-docs` красный, значит, содержимое неправильное — исправляйте содержимое, никогда не проверку. Каждое сообщение об ошибке говорит, как это сделать. Если вы считаете, что неправа́ *проверка*, поднимите вопрос на office hours; изменение проверок — это осознанное командное решение, а не локальная правка.
3. **Никогда не редактируйте сгенерированные файлы вручную** (`openspec/index.*`, хранилищный `catalog.*`). Они регенерируются; ваша правка умрёт, а CI покраснеет. Сообщение об ошибке называет команду, которая их регенерирует.
4. **Одна и та же проблема три раза → остановись и спроси человека.** Относится и к вам, и к агенту. Зацикливание — никогда не ответ.
5. **Порядок доверия для вопроса «как система себя ведёт»: код > спека репозитория > индекс репозитория > центральный каталог > вики.** Вики — это сгенерированное зеркало: читайте его, но никогда не ссылайтесь на него как на доказательство.
6. **Путь эскалации:** еженедельные office hours · чемпионы для вопросов «как мне…» · комментарий в трекере к истории для вопросов по содержимому · никогда не блокируйтесь молча.

## Аналитик

**Что меняется для вас:** вы перестаёте писать документы с требованиями с чистого листа. Агент берёт у вас интервью и составляет черновик; вы отвечаете, исправляете и утверждаете. Вы никогда не касаетесь git — вообще.

**На каждую историю:**
1. Создайте/уточните историю в трекере, как сегодня.
2. Откройте сессию агента и запустите `corp-spec <story-id>`. Агент сам подтягивает историю + связанные вики-страницы, читает текущую живую спецификацию для этой capability, проверяет реальный код, а затем задаёт вам вопросы **по одному**. Отвечайте из бизнес-знания; смело говорите «не знаю» — открытый вопрос в спеке лучше догадки.
3. Следите за подсказками агента о реальности кода («сегодня система на самом деле делает X в этом крайнем случае — оставить или изменить?»). Это золото: решения, которые никто никогда не записывал.
   **Новая функциональная область** (capability, которой пока нет ни в одном индексе)? Агент остановится и спросит, какой репозиторий должен ею владеть — если вы не знаете, это вопрос к техлиду, а не догадка; первый коммит закрепляет имя.
4. Просмотрите получившуюся делта-спеку **как отрендеренную страницу** (зеркало вики или превью PR — смотря что вам показали при онбординге): требования + сценарии Given/When/Then. Исправляйте формулировки, говоря агенту, а не редактируя файлы.
5. Утверждение = ваше обычное действие утверждения (статус в трекере или кнопка approve в PR — по настройке команды). Ничто не двигается дальше без него.
6. **Поправки:** во время реализации разработчик может прислать вам «реализация обнаружила нюанс X; предлагаемая поправка к спеке — утверждаешь?». Она приходит как небольшой диф. Прочитайте, решите, ответьте в трекере. Это минуты, а не совещания — и каждая делает базу спеки умнее.

**Никогда не делайте:** не вставляйте требования из старых вики-страниц в интервью, не проверив, что они всё ещё верны (агент сверяет с кодом — дайте ему это сделать); не утверждайте спеку, чьи сценарии вы не могли бы отдать тестировщику как есть.
**Планка качества:** у каждого требования есть хотя бы один сценарий; каждый сценарий исполним ручным тестировщиком без единого вопроса к вам.

## Backend-разработчик (JVM / потоковая обработка)

**Что меняется для вас:** вы переходите от набора большей части кода к его *направлению и ревью*. Спека отвечает на вопросы, которыми вы раньше прерывали аналитика. Написать любую историю или любую задачу руками остаётся вашим правом.

**На каждую историю:**
1. Возьмите историю; утверждённая делта-спека уже в репозитории. Прочитайте её — она короткая.
2. Запустите `corp-plan`. Планы генерируются **сейчас**, против сегодняшнего кода — никогда не доверяйте устаревшему плану; регенерация бесплатна. Просмотрите `design.md`/`tasks.md`: вы проверяете *подход*, то же суждение, что и раньше, минус набор текста.
3. Запустите `corp-implement`. Агент работает задача-за-задачей: сначала падающий тест из сценария (быстрый юнит-уровень), затем код, затем свидетельство, затем следующая задача. Ваша работа, пока он идёт: отвечать на его вопросы, выборочно проверять дифы по мере их появления, вмешиваться, как только подсказывает чутьё.
4. **Когда агент останавливается на расхождении спеки/кода**, он предлагает классификацию — решение за вами, одно нажатие клавиши:
   - **(a) спека неполна** → агент составляет поправку, пингует аналитика, вы ждёте утверждения дифа (или продолжаете другую задачу);
   - **(b) код удивителен, спека всё же верна** → планы регенерируются, продолжайте;
   - **(c) спека нереализуема** → жёсткий стоп; вы + аналитик пересматриваете. Никогда не «трактуйте контракт творчески» — эти данные потребляют нижестоящие продукты.
5. PR как всегда — спека и код в одном дифе. `corp-review` даёт вам структурированное предварительное ревью, прежде чем товарищи по команде потратят время. Если ребейз приносит конфликт **внутри `openspec/specs/`**, значит, другая история изменила то же требование — что верно сейчас, решает аналитик; не разрешайте текст контракта в одиночку.
6. После мерджа, на обновлённом main: запустите `corp-archive` — сворачивает делту в живую спецификацию, составляет черновик ADR, регенерирует индекс. Затем отметьте историю. (История не завершена, пока не заархивирована — незаархивированные изменения невидимы следующему автору спеки.)
7. **Межрепозиторная история?** Используйте ручной чек-лист в пакете харнесса §D — сначала производитель, факты контракта живут только в хранилище, весь список — на вас.

**Специфика стека:** держите разделение быстрого/медленного тест-уровня честным — юнит-тесты во внутреннем цикле, Testcontainers/context-boot тесты только на границах задач (ошибка DI-проводки всплывает только на медленном уровне; прогоните его, прежде чем объявлять задачу готовой). Задания стрим-процессора: тесты его operator-test-харнесса/embedded-кластера — это юнит-уровень, тот же ритм.
**Никогда не делайте:** не позволяйте агенту отметить задачу готовой без вставленного прогона теста; не чините красную проверку диспозера, ослабляя её; не редактируйте чекбоксы в `tasks.md` руками, чтобы «догнать» — заголовок и галочки — это память проекта.

## Frontend-разработчик (JS-фронтенд)

Тот же скелет, что и у backend — спека → план → реализация → PR — с двумя отличиями:

1. **Сценарии описывают видимое пользователю поведение** («Given an expired session, when the user submits, then show X and preserve the form»). Толкайте интервью аналитика к состояниям и крайним случаям: загрузка, пусто, ошибка, права. Агент превращает именно их в компонентные тесты.
2. **Ваш медленный уровень — визуальный.** После того как задачи агента позеленели, запустите приложение/Storybook и *посмотрите* на каждое изменённое состояние; приложите скриншоты «до/после» к PR (пока команда не выберет автоматический визуально-диф-гейт, ваши глаза — это тот гейт; относитесь к скриншотам как к вставленному свидетельству, которое backend-разработчики дают с прогонами тестов).

Компетентность агента в этом стеке наивысшая — ожидайте, что будете принимать больше и направлять меньше, чем ваши backend-коллеги, но интерактивное поведение (фокус, клавиатура, асинхронные гонки) проверяйте сами; именно там сгенерированные тесты слабее всего.

## Тестировщик (ручной QA)

**Что меняется для вас:** вы перестаёте реверс-инжинирить «что мне тестировать» из заголовков историй. Сценарии спеки — ваша тестовая основа, и они существовали *ещё до того, как код был написан*.

**На каждую историю:**
1. Когда история доходит до вас, откройте её делта-спеку отрендеренной: **Фаза 1 = файл спеки, отрендеренный в форже (ваш онбординг показывает где); зеркало вики, как только оно заработает в Фазе 2** — затем добавьте в закладки страницу каталога; она связывает каждую capability.
2. Запустите `corp-test-plan <change>` (или попросите разработчика истории — по настройке команды): сценарии становятся чек-листом, опубликованным в трекере. Просмотрите его — **добавьте то, что спека упустила**; ваше исследовательское чутьё — это ценность, которую система сгенерировать не может.
3. Исполняйте; заводите баги ровно как сегодня, но ссылайтесь на ID требования (например, «R3 нарушено: …»). Именно этот ID позволяет агенту воспроизвести, а аналитику — мгновенно найти сломанный контракт.
4. Баг в *поведении, которое спека никогда не покрывала*, — это пробел спеки; скажите об этом в баге; он становится небольшой делтой, и через квартал вы сами найдёте его в чек-листе автоматически.

**Опционально, но золото (привычка Фазы 2):** просматривайте сценарии в момент утверждения спеки — «тестируемо ли это в таком виде?» — поймать нетестируемое требование до того, как код существует, — самый дешёвый баг, который вы когда-либо найдёте.
**Никогда не делайте:** не тестируйте против того, что делает код, называя это ожидаемым; спека — это контракт; если код и спека расходятся, это находка, чем бы она ни разрешилась.

## SDET / инженер автотестов

**Что меняется для вас:** меньше написания шаблонного кода; больше владения набором тестов и, со временем, охраны проверок, которые агент не может обмануть.

**На каждую историю:**
1. После мерджа (или параллельно из утверждённой спеки) запустите `corp-autotest <change>`: скелеты тестов, выведенные из сценариев, для вашего фреймворка.
2. Закалите их — ассерты, подготовка данных, стабильность. Сгенерированные скелеты — это леса, а не готовый продукт; на наборе стоит ваше имя, а не агента.
3. Отклоняйте скелеты, которые проверяют детали реализации вместо поведения из сценария — регенерируйте с обратной связью. Тесты уровня поведения переживают рефакторинги; тесты уровня деталей гниют.

**Фаза 2+ — ваше повышение:** вы владеете **held-out гейтами** — контрактными тестами и проверками совместимости, которые бегут в credential-scoped CI-задачах, которые реализующий агент не может ни прочитать, ни отредактировать. Правила: никогда не переносите held-out тест в репозиторий, где работает агент; никогда не пускайте его учётные данные в обращённую к агенту задачу; сбой held-out *всегда* расследуется, а не «чинится» касанием гейта.

## DevOps

**Что меняется для вас:** разовая настройка (руководство по внедрению §0a–§4 — строит реализующий агент, вы даёте доступ и делаете ревью), затем тонкое установившееся состояние. Вы владеете *харнессом*, а не спеками.

**Установившееся состояние:**
1. **Следите за задачей каталога.** RED-запись = индекс репозитория сломан или недостижим — относитесь как к падающей сборке: громко, с назначенным ответственным, чините в тот же день. STALE = отдаётся последняя хорошая версия данных; допустимо на часы, но не на дни.
2. **Пины версий — ваши:** версия OpenSpec, lefthook, вендоренные скрипты. Апгрейды идут через ветку + повторный прогон тест-матрицы §11, никогда прямо в main. То же для порта: любой апгрейд порта → перезапустите пробы port-facts (P1–P8) перед раскаткой; тихая смена формата там осиротит каждую команду.
3. **Онбординг нового репозитория** = руководство по внедрению §2 (час); добавьте его в `repos.json`; каталог его подхватит.
4. **MCP-эндпоинты + настройки шлюза** — распределение и здоровье; доступ агента к трекеру/вики/LSP теперь инфраструктура; мёртвый MCP-сервер — это общекомандный отказ потока аналитика.
5. **Разделение учётных данных** (Фаза 2): обращённые к агенту CI-задачи и задачи held-out-гейта никогда не должны делить учётные данные — эта граница и есть весь смысл; проверяйте её при каждом касании конфигурации CI.

**Никогда не делайте:** не хот-фиксите сгенерированные файлы в хранилище; не выдавайте обращённой к агенту полосе доступ «временно»; не апгрейдите инструменты и харнесс в одном изменении (по одной переменной за раз — вы скажете себе спасибо, когда матрица покраснеет).

## Где что живёт (все роли)

| Что | Где |
|---|---|
| Какие capability существуют, кто чем владеет | хранилищный `catalog.md` (или его вики-рендер) |
| Текущее поведение capability X | `openspec/specs/<x>/spec.md` того репозитория (живая спецификация) |
| Что меняется прямо сейчас | `openspec/changes/<id>/` репозитория (предложение, делта, задачи, исследование) |
| Почему решено именно так | заметки ADR (только-добавление), связанные из спек |
| Как работает сам этот харнесс | руководство по внедрению + `port-facts.md` в хранилище |
